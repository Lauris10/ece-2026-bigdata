# Lab 2 - Object storage with S3: Kubernetes Job questions

## Why are the credentials stored in a Secret and not in the ConfigMap?

A ConfigMap is stored in plain text in etcd and is easily readable by anyone with cluster access or debugging tools.
A Secret benefits from extra protections in Kubernetes: restricted access via RBAC, optional encryption at rest in
etcd, and values hidden by default in tools like `kubectl describe`. Sensitive data (passwords, API keys, tokens)
always belongs in a Secret; non-sensitive configuration goes in a ConfigMap.

## The credentials of Onyxia are temporary. What happens if the Job is executed again tomorrow? How would a production platform provide credentials to a Job?

Onyxia's credentials expire after a few hours. Running the Job again tomorrow with the same Secret would fail with
an authentication error (ExpiredToken), since the stored credentials would no longer be valid.

In production, static long-lived credentials stored in a Secret are avoided. Instead, credentials are generated
on the fly, right before the Job needs them, using an IAM role attached directly to the pod or Kubernetes service
account (e.g. IRSA on AWS EKS, or Workload Identity on GCP). This removes the need to store and manually rotate keys.

## How would you turn this Job into a daily ingestion?

Replace the Job with a CronJob, which has the same structure but adds a `schedule` field in cron format
(e.g. `"0 2 * * *"` for every day at 2 AM). Kubernetes then automatically creates a new Job at each scheduled run.
