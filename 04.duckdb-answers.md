# Lab 4 - DuckDB SQL analytics: questions

## Why does `approx_unique` return 40 and 3167 instead of 50 and 2829?

`SUMMARIZE` computes an *approximate* distinct count (using a probabilistic algorithm similar to HyperLogLog),
not an exact count. On small datasets like this one, the approximation can differ noticeably from the real
number. An exact count would require `count(DISTINCT ...)` instead.

## Which issue may occur with a large file whose first rows are not representative?

DuckDB infers column types from a sample of the file (the first rows by default). If that sample isn't
representative (e.g. a column holds integers in the first rows but decimals or text further down), DuckDB may
pick a type that is too narrow (e.g. `BIGINT`), causing the read to fail or truncate once it reaches
incompatible rows. The fix is to increase the sample size (`sample_size`), force explicit types
(`types = {...}`), or relax parsing with `strict_mode = false`, as done in this lab.

## Why is the `uuid` column barely compressed?

UUIDs are random 36-character identifiers, unique for every row (2829 distinct values). Since there is no
repetition or pattern to exploit, dictionary encoding (effective for low-cardinality columns like `product`)
doesn't help, and generic compression (SNAPPY) finds very little redundancy in random-looking text.

## Why is the compressed size of some columns larger than their uncompressed size?

This happens with the `date` column here (22667 compressed vs 22661 uncompressed). On a column that is
already dense in information (few repetitions, like precise microsecond timestamps), the compression
algorithm adds a small overhead (block headers, metadata) without being able to meaningfully shrink the
actual data, so the compressed result ends up slightly larger than the original.

## Why is partitioning by `uuid` a bad idea?

Each `uuid` is unique (2829 distinct values for 2829 rows), so partitioning by `uuid` would create one
Parquet file per row. On object storage this massively multiplies the number of small objects, which is
inefficient: each file carries a fixed cost (metadata, Parquet footer overhead, per-request network latency),
so a multitude of tiny files badly hurts performance compared to a handful of larger files.

## Which partition column would you choose for a dataset of orders growing every day?

A date-based column (e.g. partitioning by day or by month, `date_trunc('day', date)` or
`date_trunc('month', date)`). This matches the natural access pattern (queries often filter on a recent
period), keeps a reasonable number of partitions, and makes it easy to add new partitions over time without
rewriting the old ones.

## How many row groups does the file contain, and how many are skipped by the filter `date >= '2100-01-01'`?

The file has 3 row groups. All 3 are skipped (0 scanned): the highest `stats_max` across the row groups is
`2048-10-17`, so none of them can contain a row after January 1st, 2100. DuckDB determines this purely from
the footer statistics, without touching the actual data — consistent with the 16 KiB transferred for that
query (metadata only).

## The orders are sorted by date. What would happen to the efficiency of the filter if they were shuffled?

Each row group would then contain a mix of dates spanning the whole time range of the dataset. The min/max
statistics of every row group would largely overlap, making statistics-based pruning nearly useless: DuckDB
could no longer safely exclude any row group and would have to scan all of them, losing the benefit of
partition/row-group filtering entirely.

## Compare the execution time of the CSV and Parquet queries. Which part of the difference is due to the network, which part to the parsing of the CSV file?

CSV: 1.25s for 28.2 MiB transferred. Parquet (same aggregation): 0.367s for 203.5 KiB. Most of the gap
(~0.88s) comes from network transfer: downloading 28 MB takes much longer than 200 KB. The rest comes from
parsing: CSV is plain text that must be split on commas, typed and converted row by row, while Parquet is
already binary and column-encoded, which is far cheaper to decode.
