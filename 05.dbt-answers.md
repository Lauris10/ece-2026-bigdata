# Lab - Bronze to Silver transformation with dbt and DuckDB: questions

## Bronze layer

**The bronze CSV files are left untouched. What is the benefit when a bug is found in a transformation, six months later?**

The raw data remains the source of truth. After fixing the transformation, the silver layer can be rebuilt entirely
from the original files, with no data lost or altered. If the bronze layer had been modified, the original information
could not be recovered.

**Which other format and layout would you choose if the orders were ingested every hour for years?**

Parquet instead of CSV: it is columnar, compressed and typed, so queries read only the columns they need. The files
would be partitioned by date (for example `bronze/orders/year=2026/month=10/day=28/`) so that queries filtering on a
date only read the relevant partitions, instead of scanning one growing file. A table format such as Iceberg or Delta
could be added for transactions and incremental loads.

## Silver layer

**The silver models are views. What happens when a view is queried, and when is it preferable to a table?**

A view stores only the SQL query: every time it is queried, the query runs again on the underlying data (here, the CSV
files on S3). The result is always fresh and no storage is used. A view is preferable when the transformation is cheap,
the data is small or must always be up to date. A table is preferable when the transformation is expensive or the model
is queried often, since the work is done once.

**`UUID` values are stored in 16 bytes. How many bytes does the `VARCHAR` representation use?**

The textual form has 36 characters (32 hexadecimal digits and 4 hyphens), so at least 36 bytes, more than twice the
16 bytes of the native type, plus the storage overhead of strings.

## Data tests

**Which strategy would you choose for a dashboard displaying the age of the customers? For a dashboard displaying the sales per region?**

For the age dashboard, the invalid birthdates would give wrong ages, so I would replace them with NULL (or reject the
users) and exclude them from the computation. For the sales per region, the birthdate is not used and the orders are
valid, so I would accept the issue and only monitor it with a warning: rejecting those orders would remove real sales
from the figures.

**The addresses associate states with random zip codes, `KY 01352` for example. Which test would detect it, and which reference data would it require?**

A test checking that the zip code belongs to the range of valid zip codes of its state, for example a
`relationships`-like test or a singular test joining the users with a reference table. It requires reference data
mapping each state to its zip code ranges (or each zip code to its state), such as an official USPS dataset, loaded as
a dbt seed or as a source.
