# Lab - Bronze to silver with Spark DataFrames: questions

## SparkSession with S3 access

**The credentials are temporary. What happens to a running Spark job if the service is restarted mid-lab, and why?**

The job is lost. The Spark driver runs inside the same container as the VS Code service, so restarting the service kills
the process and nothing resumes it. We saw it during the lab: after a restart the job had stopped and the home directory
had been reset (the ~/.aws files disappeared) while /home/onyxia/work was kept. Even without a restart, the credentials
given to S3A are fixed when the session starts. They are STS credentials with a limited lifetime (the Onyxia token showed
a maximum duration of 12 hours) and Spark does not renew them, so a long job would start failing with authentication
errors once they expire.

**Why does a plain SimpleAWSCredentialsProvider fail here, while it worked in setups without a session token?**

SimpleAWSCredentialsProvider only reads an access key and a secret key. STS credentials are a triplet: access key, secret
key and session token, and the storage rejects every request which does not carry the token.
TemporaryAWSCredentialsProvider also reads fs.s3a.session.token and sends it with each request.

## Write the silver layer as Parquet

**List the objects written under silver/users.parquet/. How many part-files are there, and why?**

There is a _SUCCESS marker of 0 bytes, written by the committer at the end of the job, and a single data file
part-00000-....snappy.parquet of 9581 bytes. orders.parquet/ has the same layout with one part-file of 139556 bytes. Spark
writes one file per output partition, and a single task writes each file. Here there is one partition, most likely
because the CSV files are read with multiLine=True, which prevents Spark from splitting them.

**coalesce(1) before .write would produce a single file. What do you lose by doing that on a larger dataset?**

The parallelism of the write: a single task has to write all the data, so the job is slower and the memory and the disk of
one executor become a bottleneck. A failure restarts the whole write, and the result is one big file which is hard to
read in parallel afterwards. Partitioned output with several moderate files scales much better.

## Write the silver layer as Iceberg tables

**Compare silver/orders.parquet/ and warehouse/silver/orders/. Which files hold the data, and which ones describe the table?**

In the plain Parquet directory there are only the data file and the _SUCCESS marker: nothing describes the table, the schema
lives in the footer of each file and the directory itself is the table. In the Iceberg table, the data/ directory holds
the Parquet data file (about 84 KB for orders), and the metadata/ directory describes the table: v1.metadata.json (schema,
partition spec and list of snapshots), a snap-....avro manifest list for the snapshot, a ....-m0.avro manifest listing the
data files with their statistics, and version-hint.text, a one-byte file which tells a reader the current metadata version.
The Iceberg data file is smaller than the Spark Parquet one (about 84 KB against 139 KB), probably because of a different
default compression codec, which I did not verify.

**A second job overwrites the Parquet directory while a query is reading it. What does the reader see? What changes with an Iceberg table?**

With a Parquet directory the overwrite deletes and rewrites files while the reader is listing and reading them, so the
reader can fail on a file which disappeared, read a mix of old and new files, or find an empty or incomplete directory.
Nothing makes the change atomic. With Iceberg the reader works on the snapshot it opened: the new data files are written
first and the commit atomically switches the table to the new metadata, so the reader sees either the old version or the
new one, never a half-written table.

**With this catalog, the pointer to the current version of a table is a file in the bucket. What can go wrong if two jobs commit at the same time, and what would a catalog service add?**

The hadoop catalog commits by writing a new metadata file and updating the pointer, which relies on an atomic rename or an
atomic create, and an object store does not provide that natively (a rename is a copy followed by a delete). Two jobs can
overwrite each other's metadata, so one commit is lost, or the table is left inconsistent. A catalog service (a REST
catalog such as Polaris, a Hive metastore or a JDBC catalog) holds the pointer in a transactional store and makes the
commit a compare-and-swap: the second job is rejected and retries on the new version. It also centralizes access control
and lets several engines share the same tables.

## Compare with the dbt lab

**What differs between the two schemas? Spark has no UUID type: what did you do about it, and what is the consequence for the consumers of the silver layer?**

In the dbt output, order_id and user_id (and user_id in users) are UUID, and ordered_at is TIMESTAMP WITH TIME ZONE. In the
Spark output they are VARCHAR, and DuckDB reads ordered_at as a TIMESTAMP without time zone. The other columns are the
same. Since Spark has no UUID type, I cast the identifiers to string. The consequence is that each identifier takes 36
characters instead of 16 bytes, the file is bigger and the joins and comparisons are slower, and nothing checks that a value
is a valid UUID. A consumer has to cast the columns to get the type back, and a join between a dbt table and a Spark table
needs an explicit cast. For the timestamp, the consumers must know that the values are in UTC.

The counts match: both outputs have 2829 orders with a total quantity of 8615, and 50 users.

**Compare the output layout: one object per model with dbt, one directory of part-files with Spark. Which one is easier for a consumer to read? Which one scales?**

One object per model is easier to read: a single path, with no glob and no marker file to ignore. A directory of
part-files has to be read with a glob (and the _SUCCESS file skipped), which is less convenient. But a single object does
not scale: one process writes it and it cannot be partitioned. The directory of part-files is written in parallel, can be
partitioned by date or by key and is read in parallel, so it is the one which scales. An Iceberg table keeps that layout
and adds table semantics on top.

**The dbt lab validates the silver layer with the unique, not_null, accepted_values and relationships tests. What did this lab use instead, and what would you need to write to get the same guarantees?**

This lab only used ad hoc checks: comparing the number of rows between steps with assertions, and a groupBy count to look
for duplicates. They run once, by hand. To get the same guarantees I would write each test as code and run it after every
build, failing the job on a violation: unique is a groupBy on the key with a count above 1, not_null is a filter on null
values, accepted_values is a filter on values outside the list, and relationships is a left anti join of orders on users.
A library such as Great Expectations, Soda or Deequ provides these checks ready to use.

**ref() and source() give dbt the dependency graph of the models. What plays this role in the notebook?**

Nothing explicit. The dependencies are implicit in the Python variables and in the order of the cells: stg_orders is built
from orders_typed, which is built from orders_bronze. Spark knows the lineage of each DataFrame to execute it (explain()
shows it), but the graph of the whole pipeline, the documentation and the ability to rebuild only a part have to be
maintained by hand or by an orchestrator such as Airflow or Dagster.

**Compare the time to build the silver layer with dbt build and with the cells of this lab. Why are these numbers not directly comparable?**

dbt build took about 4.4 seconds for the 2 models and the 14 tests. The Spark script took minutes: starting the JVM and the
session, downloading the Iceberg package, reading the CSV files from S3, and writing the Parquet files and the Iceberg
tables. The numbers are not comparable because the dbt models are views, which only store a query and write no data (the
Parquet export was a separate step), and DuckDB is embedded so it has no startup cost. Spark also ran in local mode in a small
container of about 2 GB, and wrote more outputs.

**For each of these cases, would you choose dbt with DuckDB or Spark: a daily batch of 10 GB, a daily batch of 10 TB, a team of analysts who only know SQL?**

A daily batch of 10 GB: dbt with DuckDB. A single machine handles tens of gigabytes, it is simple and cheap to operate. A
daily batch of 10 TB: Spark, or another distributed engine, because the data does not fit the memory, the disk and the time
budget of one machine. A team of analysts who only know SQL: dbt, since it is SQL first and brings tests, documentation and
lineage; Spark SQL is possible but means operating a cluster.

### 2. regexp_extract against a Python UDF and a pandas_udf

Timings on the cached address column, 3 runs each (minimum and mean):

| Version | Minimum | Mean |
|---|---|---|
| regexp_extract (native) | 0.138 s | 0.212 s |
| Python UDF | 0.158 s | 1.012 s |
| pandas_udf | 0.156 s | 0.553 s |

The native function is the fastest: it runs inside the JVM and Catalyst can optimize it. A Python UDF sends the rows one by
one to a Python worker, which Spark cannot optimize. The pandas_udf sends batches through Arrow, which is cheaper than the
row by row UDF on large data, but it still crosses the JVM and Python boundary. With only 50 rows and 3 runs measured by hand
(not with %%timeit), the minimums are close and the means mostly show the startup cost of the Python workers, so the ranking
is only indicative.
