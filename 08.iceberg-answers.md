# Lab - Explore Iceberg tables with Spark: questions

The tables used in this lab, lab.silver.orders and lab.silver.users, were created in the Spark DataFrame lab (lab 07), and the
exercise 4 of that lab had already appended one order to lab.silver.orders. The orders table therefore started this lab with
2 snapshots instead of 1.

## Inspect the files

**Which files contain the actual rows?**

The Parquet files in the data/ directory. For orders there are 4 of them in the end: 00000-21-....parquet (84055 bytes, 2829
rows), which is the original one, and 3 small files created by the later appends and by the insert.

**Which files describe the table?**

The files of the metadata/ directory: the table metadata files v1.metadata.json to v5.metadata.json (schema, list of snapshots,
current snapshot), one snap-....avro file per snapshot (the manifest list of that snapshot), the ....-m0.avro manifests (which
list the data files with their statistics), and version-hint.text, a one-byte file which tells a reader the current version.

**Why does an Iceberg table need more than the Parquet files?**

A set of Parquet files does not say which files belong to the table, in which order they were added, what the schema of the
table is, or what the table looked like before. The metadata gives the table a defined state: the exact list of files, the
schema, the history of the versions, and a way to switch from one version to the next in one step. Without it, a reader
can only list the directory and trust whatever is in it.

## Explore Iceberg metadata

**How many snapshots does the table currently have?**

At the start of the lab, 2: an overwrite (the creation of the table) and an append (the order added in lab 07). The lab
expects 1, since it assumes a table created just before.

**How many data files belong to the current table?**

2 at the start (the original file with 2829 rows and a file with 1 row), 3 after the append of this lab and 4 after the insert
with the new column. In the end the 4 files hold 2829 + 1 + 3 + 1 = 2834 rows.

**What information does the snapshots table contain that the Parquet files do not?**

Its columns are committed_at, snapshot_id, parent_id, operation, manifest_list and summary. So it says when a version was
committed, by which kind of operation (overwrite, append), which version it follows, which manifest list describes its files,
and a summary of the changes. A Parquet file only holds its own schema and statistics, and nothing about its history.

## Create a second snapshot

**How many snapshots are there now?**

3 after appending the 3 new orders (the table then had 2833 rows), and 4 after the insert of the schema evolution step.

**Did the original Parquet files disappear?**

No. The original file (84055 bytes, 2829 rows) is still there and still belongs to the current table, as the files table shows.
The append only added a new data file of 3 rows, and a new snapshot which lists the old files and the new one.

**Why does Iceberg create a new snapshot instead of simply replacing the table?**

Because a snapshot is an immutable, complete description of the table at one moment. Writing a new one leaves the previous
versions intact, so a reader which is already running keeps a consistent view, the change becomes visible all at once when it is
committed, and the old versions stay available for time travel or for a rollback.

## Time travel

**What does time travel read?**

It reads the table as described by an older snapshot: the data files listed in the manifests of that snapshot, with the schema
of that moment. With VERSION AS OF the first snapshot, the query returned 2829 rows, when the table had 2833 at that time.

**Why can Iceberg access an older version without making a complete copy of the table?**

The data files are immutable and shared between the versions. A snapshot is only a list of references to files, so the old and
the new version mostly point to the same Parquet files, and only the metadata and the new files are written.

**What would happen if the old snapshot's metadata and data files were physically deleted?**

Time travel to that version would fail, since the files it needs are gone. The deleted files may also be shared with the
current version: the original file with 2829 rows belongs to every snapshot, so deleting it would damage the current table.
Old versions should be removed with the table maintenance operations (expiring snapshots), which only delete the files which are
no longer referenced.

## Schema evolution

**Did the existing Parquet files have to be rewritten?**

No. The original file kept the same size (84055 bytes) and the same 2829 rows, and the insert wrote a new data file of 2201
bytes, which includes the source column. For the older files, the new column simply reads as NULL.

**Where is the new schema recorded?**

In the table metadata: ALTER TABLE created a new version of the metadata file (the orders table went from v3 to v4, then to v5
with the insert) which contains the new schema. The data files keep the schema they were written with. The first snapshot still
returns the old columns (no source) in time travel, so each snapshot keeps its own schema.

**Why is schema evolution a table-level operation rather than simply changing a Parquet file?**

The schema belongs to the table, which is made of many files written at different times, while a Parquet file is immutable and
holds its own schema in its footer. Changing the table schema in the metadata is instant and does not touch the data, and it
lets old and new files be read together. Rewriting the files would be slow and would change the history.

## Compare Iceberg with Parquet

**Which one is simply a collection of Parquet files?**

silver/spark/orders.parquet/: the part-files and the _SUCCESS marker, nothing else. The table is only the directory.

**Which one has table metadata and snapshots?**

warehouse/silver/orders/, with its metadata/ directory (5 metadata files, 4 manifests and 4 manifest lists) next to the data/
directory.

**How would you safely replace a Parquet directory while another query is reading it?**

Not in place. I would write the new version in a new directory (for example with a version or a date in its name), then switch
the readers to it in one step, by updating a view, a configuration or a pointer, and delete the old directory only after the
queries which read it have finished. An in-place overwrite lets a reader see missing or mixed files.

**How does Iceberg make the table state visible atomically?**

The data files and the new metadata files are written first, and they are invisible because nothing points to them. The commit
is the single step which switches the table to the new metadata file (here the version-hint.text file, in general the pointer
kept by the catalog). A reader sees either the old version or the new one, never a half-written table.

**Why is a catalog needed once several engines need to share the same Iceberg table?**

The engines must agree on where the current metadata of a table is, and on how to commit a change without overwriting another
engine's commit. A catalog gives the tables a name, stores the pointer to the current metadata, makes the commit atomic and
rejects a conflicting one, and also centralizes the access rights. With the hadoop catalog of this lab, which is only a
directory in the bucket, two engines writing at the same time could overwrite each other.

### 1. Create lab.silver.users as an Iceberg table

The table already existed, written in the Spark DataFrame lab with writeTo(...).createOrReplace(). I did not create it again,
since that would have replaced the table and cut its history. It has 50 users and one snapshot (operation overwrite).

### 2. Append a new batch of users and inspect the snapshots

I appended 3 users, copied from existing ones with a new uuid, a username ending with _new and an email starting with new_ (so
that the usernames and emails stay unique). The table now has 2 snapshots (the overwrite and the append) and 53 users, and a
new data file of 3 rows (3355 bytes) next to the original file of 50 rows (7436 bytes).

### 3. Time travel before and after the append

With VERSION AS OF the first snapshot, the query returns 50 users, and the current table returns 53. Both read the same
original data file, and the second one adds the file of the append.

### 4. Add a country column and write new data with the evolved schema

ALTER TABLE ... ADD COLUMN country STRING, then I appended 2 users with the country US. The table has 55 users, 53 with a NULL
country (the existing rows) and 2 with US. The columns at the first snapshot do not include country, and the current table
has it, so time travel returns the old schema. The existing files were not rewritten. The table now has 3 snapshots.

### 5. Compare the S3 layout of the users and orders tables

| | orders | users |
|---|---|---|
| Data files | 4 (2829, 1, 3 and 1 rows) | 3 (50, 3 and 2 rows) |
| Manifests (m0.avro) | 4 | 3 |
| Manifest lists (snap-....avro) | 4 | 3 |
| Metadata files (vN.metadata.json) | 5 (v1 to v5) | 4 (v1 to v4) |
| Snapshots | 4 | 3 |

The layout is the same: a data/ directory and a metadata/ directory with a version-hint.text file. The numbers depend on the
number of operations. Each commit of data adds a snapshot, a manifest list, a manifest and a metadata file. A schema change
adds a metadata file but no snapshot, which is why there is one more metadata file than snapshots (the schema change) for orders and
for users, and the user table is one commit shorter than orders. The original data file of each table is untouched.

### 6. Difference between Parquet, Iceberg and an Iceberg catalog

Parquet is a file format: a columnar, compressed file which holds rows with their schema and statistics. A directory of
Parquet files is only a set of files, with no table state. Iceberg is a table format built on top of Parquet files: it adds
metadata (schemas, snapshots, manifests) which defines the table as an exact list of files with a history, and makes changes
atomic, so it offers time travel, schema evolution and isolation between readers and writers. An Iceberg catalog is the service
or the directory which knows the tables: it maps a table name to its current metadata file and performs the atomic commit
which switches a table to a new version, so that several engines can share the same tables.
