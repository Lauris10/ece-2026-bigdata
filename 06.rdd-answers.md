## RDD creation and partitions

**What decides the number of partitions `textFile()` picks by default, for a file this size?**

Spark splits the file according to its size and the block size (128 MB by default), with a minimum number of
partitions (`minPartitions`, 2 by default). The two CSV files are only a few KB, so they get the minimum: 2 partitions
each, which is what was observed.

**`repartition()` and `coalesce()` both change the partition count. Which one shuffles data, and which one doesn't?**

`repartition()` triggers a full shuffle and can increase or decrease the number of partitions, with balanced
partitions. `coalesce()` avoids the shuffle by merging existing partitions locally, so it can only decrease the number
of partitions, and the result may be unbalanced.

## Lazy evaluation and lineage

**Call `orders_data.count()` a second time. Does the Spark UI show a new stage? Why?**

Yes, each action launches a new job. Nothing is cached, so Spark replays the whole lineage: it reads the file again
and applies the filter again.

**At which point in this notebook would `.cache()` change that answer?**

Calling `.cache()` on `orders_data` before the first `count()`. The first action then stores the partitions in memory,
and the second one reads them from memory instead of rereading and refiltering the file.

## The multiline address

**Why does `spark.read.csv(multiLine=True)` not have this problem, while `sc.textFile()` does?**

The CSV reader understands quotes: with `multiLine=True` a newline inside a quoted field belongs to the field.
`textFile()` only knows about newline characters, it splits the file at every one of them without any notion of quotes
or fields. That is why the file gave 101 elements instead of 51 (the header and 50 users).

**What has to be true of a file format for a line-oriented reader like `textFile()` to be safe to use on it?**

Each record must fit on exactly one physical line: the newline must only be used as a record separator and never
appear inside a field (or must be escaped). Each line must also be parsable on its own, without depending on the
previous lines. Formats such as JSON lines satisfy this, CSV with quoted multiline fields does not.

## Manual parsing of orders

**What would happen to this cell if one line in `orders.csv` had an extra comma inside `product`?**

`line.split(",")` would return 6 values, and unpacking them into 5 variables raises a `ValueError`. Because of lazy
evaluation, the error does not appear when the RDD is defined but at the first action which processes that line, and
it fails the whole job.

**Where does the DataFrame API perform the equivalent check, and when?**

The DataFrame reader applies a schema while parsing, with a configurable mode: `PERMISSIVE` (default) puts nulls in
the fields it cannot parse, `DROPMALFORMED` drops the bad rows, and `FAILFAST` raises an error. The parsing happens
when an action runs, but the schema is known as soon as the read is defined (inferred from the file with
`inferSchema`).

## Key-value RDDs

**`reduceByKey` combines values on each partition before shuffling. What does `groupByKey` shuffle instead, and why is that more expensive?**

`groupByKey` shuffles every single (key, value) pair across the network, with no combination before the shuffle.
`reduceByKey` first reduces the values of each key inside each partition (map-side combine), so at most one value per
key and per partition is shuffled. Less data to write, transfer and read means a cheaper stage, and less memory is
needed to hold all the values of a key.

**For which aggregations would `groupByKey` be unavoidable, `reduceByKey` not being able to express them?**

When the result needs all the values of a key at once and cannot be built by combining values two by two with an
associative and commutative function: for example a median or an exact percentile, or sorting or ranking the values of
a key.

## Manual deduplication

**`partitionBy()` in the window function is described as a wide transformation. What plays that role here?**

The `reduceByKey` on `order_id`: it shuffles the rows so that all the rows with the same `order_id` end up in the same
partition, where the `most_recent` function can compare them.

**Which version states the intent more directly: the window function, or the `reduceByKey` with a custom combiner?**

The window function: `PARTITION BY order_id ORDER BY ordered_at DESC` describes the intent declaratively, and Spark
chooses how to execute it. With `reduceByKey`, the intent is hidden in a custom function and the code has to handle
details itself (here, comparing dates as strings).

## Joining orders with users

**What would need to be true of how `orders_kv` and `users_kv` are partitioned for Spark to skip the shuffle?**

Both RDDs must be partitioned with the same partitioner and the same number of partitions (for example
`partitionBy(8)` on the key for both), so that matching keys are already in the same partition. The join is then a
narrow transformation. Persisting the partitioned RDDs avoids repeating the shuffle.

**Replace `join()` with `leftOuterJoin()`. What changes in the result if a `user_id` in `orders` has no matching user?**

`join()` is an inner join: the order without a user disappears from the result. `leftOuterJoin()` keeps it, with
`None` instead of the username.

**What is the risk of calling `.collect()` on `enriched` directly, on a dataset much larger than this one?**

`collect()` brings all the elements to the memory of the driver. On a large dataset, this can exhaust the driver
memory and crash the application. It is safer to aggregate or filter first, use `take()`, or write the result to
storage.
